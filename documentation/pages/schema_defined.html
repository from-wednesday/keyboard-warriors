Keyboard Warriors · Developer Reference

Shortcut JSON Schema

To help developers wanting to build content for Keyboard Warriors, this page provides a field-by-field specification for shortcut entries in the app's JSON data files, scope and classification rules, chip rendering order, and an explanation of the JavaScript functions that read and process this data.

See the companion shortcuts token reference '</>Defining Keys' for the full list of accepted key tokens.

01 ) Entry Structure

The complete data file for any software package is a flat JSON array. Each item in that array is a single shortcut entry: One question-and-answer block for the game. These will be referred to as JSON objects, shortcut entries or simply entry.

An entry can contain up to six fields. The first four are required on every normal entry. The final two are optional and should only be added when they genuinely improve gameplay. Keep each field on its own line for clarity:

{
"display": "verb-first description of the action",
"mac_sc": "TOKEN+TOKEN",
"pc_sc": "TOKEN+TOKEN",
"difficulty": 3,
"group": "optional_group_name",
"sequential": true
}

"display"

This is the question prompt shown to the player. It must be plain text with no markup. Because of that, I like to use capital letters sparingly where I want to place emphasis.

Write it action-focused, concise, and verb-first. I like to vary the language to make the gameplay feel more conversational and less repetative. For example, "pick up the Eraser" ; "grab the Pen Tool" ; "select the Laso Tool" etc.

Avoid including (or hinting at) the answer in the display text. Aim for a phrase a player can read comfortably in a few seconds.

When writing these, consider both the context of the in-game question and the free-style exploration mode: In game the text is asking you to do something. Between games it is reporting back what function those keys perform. If you are unable to arrive at one "display" that works for both of these use cases, it is possible to define the shortcut as two JSON objects. One for each context at the exclussion of the other. See the "difficulty" and "sequential" sections below for more information.

Note that for "sequential" entries, it is essential to phrase the "display" string for the context, such as "after pressing… press this to…". More on sequential shortcuts later.

"display": "save the document" // a simultaneous chord
"display": "after entering a configuration number, store it" // sequential keys

"mac_sc"

The token string used for Mac input matching and chip rendering. Tokens are combined with +. Use the pipe | to offer alternative accepted answers where a single action genuinely has more than one accepted key.

Use the literal value NULL (or the synonym NONE) when the shortcut does not exist on Mac.

Prefer platform-native modifier tokens in Mac fields: CMD, OPT, CONTROL, SHIFT. Although the system will translate between equivallent OS keys, writing OS specific data in the other platform's conventions is more error prone because the JSON is less human-readable for proofing.

See the shortcuts token reference </>'Defining Keys' for all accepted tokens and their accepted synonyms.

"mac_sc": "CMD+S" // single chord
"mac_sc": "CMD+ARROWLEFT|HOME" // two accepted answers; chip shows first
"mac_sc": "NULL" // does not exist on Mac

"pc_sc"

The token string used for PC input matching and chip rendering. Follows exactly the same rules as mac_sc. Again, prefer platform-native modifier tokens here in PC fields: CTRL, ALT, WIN, SHIFT.

At least one of the two platform fields must contain real tokens. An entry where both are NULL is invalid.

"pc_sc": "CTRL+S"
"pc_sc": "NULL" // does not exist on PC

"difficulty"

An integer from 0 to 6 controlling which question pools the entry enters, based on the player's selected difficulty setting. Difficulty 6 is reference-only and is never surfaced in normal gameplay round. It is provided as a way to include vocabulary for free-style mode only.

See Section 04 — Difficulty Scale for the full breakdown.

"difficulty": 1 // easy — Common cross-app shortcuts
"difficulty": 3 // normal — core app knowledge
"difficulty": 5 // hard core — highly niche or particularly complex

"group" (optional)

This is not what you'd expect. There is no utility in Keyboard Warriors to simply categorising shortcuts in the ways we might if we were making notes or producing a long list.

Here "group" has a very specific purpose and should be used very sparingly.

It is a string label that strategically limits how many closely related entries can appear in any single ten-question round. You should omit this field entirely unless the entries are near-identical variants with obvious answers in context with one another. Shortcuts that would feel repetitive or interchangeable if presented together in the same round. Do not group entries simply because they share a topic. See Section 05 — Groups.

"group": "nudge"

"sequential" (optional)

I made Keyboard Warriors to learn and practice shortcut single keys and simultaneous chords. Only afterwards did I learn how many applications use sequential key combinations to perform actions. The distinction I am drawing here is that a sequential shortcut is not held simultaneously. Rather than retool the whole gameplay for this minority case, I have a pragmatic work around:

"sequential" is a boolean, always set to true when present. It marks an entry that has been remodelled from a multi-step sequential workflow into a playable initiation or completion single keykey prompt. The game excludes entries marked as "sequential" from freestyle mode where out-of-context sequential prompts would be misleading. As such, this can be used on any JSON object you wish to exclude from Freestyle Mode.

This flag is entirely separate from difficulty. Do not use difficulty 6 as a substitute for it. It is functionally the opposite effect to difficulty 6. See Section 06 — Sequential Entries.

"sequential": true

02 ) Field Reference

FieldTypeRequiredRules
display String Yes Plain text question prompt. Verb-first, concise, unambiguous, no markup, avoid answers in the text.
mac_sc String Yes Token string for Mac matching and chip rendering. Use NULL or NONE when the shortcut does not exist on Mac. At least one of mac_sc or pc_sc must contain real tokens.
pc_sc String Yes Token string for PC matching and chip rendering. Same NULL / NONE rule as mac_sc.
difficulty Integer Yes Integer 0–6. Controls the question pool. Difficulty 6 is reference-only and never quizzed in normal gameplay. See Section 04.
group String No Limits the number of the same named group objects per question pool. Only add this when near-identical variants would feel repetitive or redundant if drawn together. See Section 05.
sequential Boolean No Must be set explicitly. You only need to add this when it is true. It will then exclude the entry from freestyle mode where it will not make sense in that context. Difficulty 6 is incompatible with sequential shortcuts. See Section 06.

03 ) Scope Rules

Not every shortcut in vendor documentation belongs in a Keyboard Warriors file. The goal is a clean, verified training dataset, not a literal transcription of a vendor manual. Apply the table below during extraction to decide what to include, remodel, or leave out. You might like to classify each candidate in a working ledger before compiling the final JSON.

CategoryDefault decisionNotes
Single keypresses Keep Examples: B, TAB, SPACE, F9.
Simultaneous chords Keep Examples: CMD+S, CTRL+SHIFT+R.
Universal shortcuts (except Undo) Keep Assign difficulty 0–1. These should appear in every package where they work.
Undo Remove Project convention: do not include Undo as it is built into the app as the default fallback question. Including it would double its prevalence. If testing produces a round repeating only this question, the JSON is invalid or failed to load.
Pure mouse interactions Remove Examples: double-click, triple-click, right-click-only actions. There is no key to detect. These are out of scope for Keyboard Warriors.
Modifier-clicks and modifier-drags Keep when useful Keep when the modifier is the meaningful workflow knowledge being learned. The shortcut value should be only the modifier chord, not the mouse action itself. See Section 07.
Sequential keystrokes Remove, remodel, or mark sequential Never encode arbitrary sequences literally. Remodel into a completion-key prompt where the sequence can be made fair. See Section 06.
Menu navigation without a shortcut Remove Only include direct keypresses, chords, or approved modifier workflows.

Use the following ledger statuses when classifying candidates during extraction:

KEEP    MERGE    REMODEL    REMOVE    REFERENCE-ONLY    SEQUENTIAL-COMPLETION

04 ) Difficulty Scale

Difficulty controls which pool an entry enters relative to the player's selected difficulty setting. Distribution does not need to be equal across levels. Some professional software packages can legitimately skew harder than others. I would however aim for at least a dozen entries at each level from 0 through to 5 so that difficulty changes feel meaningfull.

Difficulty 6 is not indicative of a harder item. It is purely a functional allocation to be used when needed. It's absence from a file is not only permitted, but probably the ideal.

LevelLabelDescription
0 Ubiquitous Universal shortcuts present in virtually every app, like "Save" and "New". These should appear in every package where they work. Keep common universal shortcuts at low difficulty.
1 Common Very common cross-app fundamentals that are slightly more varied, less intuitive or apply to fewer apps. Examples: Select All, Print.
2 Logical Regular workflow shortcuts that follow a clear and obvious pattern, for example, tools whose shortcut uses the tool's initial letter (L for Line, B for Brush).
3 Intermediate The core shortcuts most serious users of the selected app need to learn. Commonly used app-specific panel toggles and key workflow commands live here.
4 Power user Advanced editing actions, modifier-click and modifier-drag behaviours, and professional workflow commands. More complex and less commonly known.
5 Hardcore Highly specialist or obscure actions and very difficult-to-remember multi-key combinations. Rarely needed but worth knowing for serious practitioners, or players wanting a challenge.
6 Reference only Never surfaced in normal difficulty tiers or gameplay rounds. Used for actions that cannot be explained clearly within a prompt readable in a few seconds, or for freestyle-only definitions that would conflict with a regular game entry. Placing a difficulty-6 entry immediately before a regular entry causes it to intercept that key combination in freestyle mode, delivering an alternative description without interfering with gameplay!

05 ) Groups

The group field prevents a run of near-identical questions from appearing together in a single ten-question round. The pool builder caps any named group at two entries per round.

Use groups sparingly. Only apply a group label when entries are near-identical and genuinely likely to feel interchangeable if drawn together in one round. Do not group entries simply because they share a topic.

Pipes vs groups

Pipes (|) handle genuinely different ways to perform the same action. Groups handle different but closely related actions that risk feeling repetitive together. When a set of actions maps to a predictable pattern of keys (such as a row of digits or the four arrow directions) a group is usually the right choice to keep any one round from feeling monotonous.

Wrong approach

{
span class="c-key">"display": "nudge",
"mac_sc": "ARROWRIGHT|ARROWDOWN|ARROWLEFT|ARROWUP",
"pc_sc": "ARROWRIGHT|ARROWDOWN|ARROWLEFT|ARROWUP",
"difficulty": 2
}

Split "nudge" into four questions and group them, rather than piping as a single JSON object.

Right approach

{
"display": "nudge Right",
"mac_sc": "ARROWRIGHT",
"pc_sc": "ARROWRIGHT",
"difficulty": 2,
"group": "nudge"
} {
"display": "nudge Down",
"mac_sc": "ARROWDOWN",
"pc_sc": "ARROWDOWN",
"difficulty": 2,
"group": "nudge"
} {
"display": "nudge Left",
"mac_sc": "ARROWLEFT",
"pc_sc": "ARROWLEFT",
"difficulty": 2,
"group": "nudge"
} {
"display": "nudge Up",
"mac_sc": "ARROWUP",
"pc_sc": "ARROWUP",
"difficulty": 2,
"group": "nudge"
}

But when there are genuinely two ways that a requested action can be accomplished in the app, the pipe can make the question fair.

Wrong approach

{
"display": "pan with the hand tool",
"mac_sc": "H",
"pc_sc": "H",
"difficulty": 2
} {
"display": "pan with the hand tool",
"mac_sc": "SPACE",
"pc_sc": "SPACE",
"difficulty": 2
}

"pan with the hand tool" works as a quick to follow question, but presented this way the player can be marked 'wrong' with an acceptible response.

Right approach

{
"display": "pan with the hand tool",
"mac_sc": "H|SPACE",
"pc_sc": "H|SPACE",
"difficulty": 2
}

Let's return to this example in Section 08, the Reference-Only Triple-Entry Pattern.

06 ) Sequential Entries

Never encode variable sequences literally. A shortcut value such as NUMPADDECIMAL+[1-99]+NUMPADADD cannot be matched by the game engine and does not represent a fair question. Remodel or remove it.

Multi-step sequential workflows are normally out of scope because encoding an arbitrary sequence as a single question produces an unfair and unplayable entry. However, some workflows can be remodelled into fair questions by placing part of the sequence into the prompt as context and then asking for the missing key.

What not to do

{
"display": "store Window Configuration",
"mac_sc": "NUMPADDECIMAL+[1-99]+NUMPADADD",
"pc_sc": "NUMPADDECIMAL+[1-99]+NUMPADADD",
"difficulty": 6
}

Invalid, never do this.

Even If we make it into 9 seperate entries for all NUMPAD1 through to NUMPAD9, 10-99 are already sequential by definition and then NUMPADADD is too.

Preferred completion-key form

{
"display": "after entering a Window Configuration number, store it",
"mac_sc": "NUMPADADD",
"pc_sc": "NUMPADADD",
"difficulty": 4,
"sequential": true
}

By placing the first part of the sequence in the display as context, we can then ask for the final key only. Phrase the prompt as "after entering…" or "to complete… press…". Always include "sequential": true on every remodelled sequential entry.

The sequential flag is independent of difficulty. Do not rely on difficulty 6 to exclude these entries from freestyle. This flag must be set explicitly on every remodelled sequential entry.

07 ) Modifier-Enhanced Mouse Actions

A blanket "no mouse actions" rule is too strict for professional creative software, where modifier-clicks and modifier-drags often represent genuine and important workflow knowledge. Keep these entries when the modifier itself is the answer being learned, not the mouse action.

Action typeDecisionExample wording
Modifier-click workflow Keep if useful toggle Mute on all tracks while clicking Mute
Modifier-drag workflow Keep if useful stretch a warped clip while dragging the clip title bar
Fine-adjust modifier Keep if useful use finer resolution while dragging a value
Pure double-click Remove double-click the track name
Right-click menu only Remove right-click to open context menu

Wording must make the mouse context explicit. Use "while clicking" or "while dragging" so the player understands what the mouse is doing during the shortcut. The shortcut value should be only the modifier or modifier chord being held — not the mouse action itself. Only keep an entry if an experienced user would genuinely benefit from memorising that modifier behaviour.

08 ) Reference-Only Triple-Entry Pattern

When a single command has both a single-key version (sometimes requiring a Keyboard Focus mode to be enabled) and a longer chord version, the playable entry should accept both answers via pipe syntax. The individual source-specific variants can be retained as difficulty-6 reference-only entries so they appear with their own wording in freestyle exploration mode without appearing in normal gameplay rounds.

adequate approach

{
"display": "pan with the hand tool",
"mac_sc": "H|SPACE",
"pc_sc": "H|SPACE",
"difficulty": 2
}

We arrived at this JSON object in the pipe example above, but we can still improve upon this.

preferred approach

{
"display": "select the hand tool",
"mac_sc": "H",
"pc_sc": "H",
"difficulty": 6
} {
"display": "hold this to quickly pan with the hand tool",
"mac_sc": "SPACE",
"pc_sc": "SPACE",
"difficulty": 6
} {
"display": "pan with the hand tool",
"mac_sc": "H|SPACE",
"pc_sc": "H|SPACE",
"difficulty": 2
}

Here Difficulty-6 has been used to add specificity to the freestyle definitions, while the in-game question is more general for fast flexible game play. Note that the order is important. Freestyle will report the first answer it finds, so we do not need to falsely label the pipe option as sequential (it isn't) it just needs to come after the difficulty 6 options.

Use this pattern sparingly where the distinction is meaningful and source-supported.
Merged playable entries should always reflect the player's perspective: one action, multiple accepted answers.Reference-only entries preserve source detail without overloading normal gameplay. They can be more verbose if it adds precision, now that reading time is not a consideration.

09 ) Platform-Only Guidance Blocks

When an app genuinely exists on only one platform, all real shortcut entries use NULL for the absent platform field. In addition, place a six-object guidance block at the very start of the file so that players on the absent platform receive a clear prompt to switch OS. The block covers all three major difficulty tiers (0, 3, and 5) so the message is seen regardless of what difficulty the player has selected.

Do not delete these as duplicates. The intentional repetition across tiers ensures the message is always visible. Keep the full block before all real app shortcut entries in the file.

Mac-only app starter block

{
"display": "Switch to Mac in the top left. Press ENTER.", "mac_sc": "NULL", "pc_sc": "ENTER", "difficulty": 0 }, {
"display": "[App Name] is a Mac only app. Press ENTER.", "mac_sc": "NULL", "pc_sc": "ENTER", "difficulty": 0 }, {
"display": "Switch to Mac in the top left. Press ENTER.", "mac_sc": "NULL", "pc_sc": "ENTER", "difficulty": 3 }, {
"display": "[App Name] is a Mac only app. Press ENTER.", "mac_sc": "NULL", "pc_sc": "ENTER", "difficulty": 3 }, {
"display": "Switch to Mac in the top left. Press ENTER.", "mac_sc": "NULL", "pc_sc": "ENTER", "difficulty": 5 }, {
"display": "[App Name] is a Mac only app. Press ENTER.", "mac_sc": "NULL", "pc_sc": "ENTER", "difficulty": 5 }

PC-only app starter block

{
"display": "Switch to PC in the top left. Press RETURN.", "mac_sc": "RETURN", "pc_sc": "NULL", "difficulty": 0 }, {
"display": "[App Name] is a PC only app. Press RETURN.", "mac_sc": "RETURN", "pc_sc": "NULL", "difficulty": 0 }, {
"display": "Switch to PC in the top left. Press RETURN.", "mac_sc": "RETURN", "pc_sc": "NULL", "difficulty": 3 }, {
"display": "[App Name] is a PC only app. Press RETURN.", "mac_sc": "RETURN", "pc_sc": "NULL", "difficulty": 3 }, {

10 ) Canonical Chip Order

Regardless of the order tokens appear in the JSON string, chips always render in a fixed canonical order. The token string itself does not need to follow this order — the parser reorders it automatically before display.

PlatformRendering order
Mac ⌘ ⌃ ⌥ ⇧ key   CMD → CONTROL → OPTION → SHIFT → key
PC Win Ctrl Alt ⇧ key   WIN → CTRL → ALT → SHIFT → key

11 ) System Component Glossary

Use these names when discussing the system in code, comments, or documentation. Each corresponds to a distinct JavaScript function.

FunctionRoleDescription
NormaliseToken( token ) Token normaliser Converts any accepted synonym to its canonical form, for example OPTION to OPT in Mac fields, or OPT to ALT in PC fields. Called first by everything else so the rest of the system only ever sees canonical tokens.
ParseShortcutString( shortcutString ) String parser Splits a token string on +, runs each token through NormaliseToken, and returns a structured object describing which modifier flags are required and what the key token is. Also splits on | first to separate piped alternatives, parsing each alternative separately.
GetActiveShortcutString( shortcutEntry ) OS selector Takes a shortcut JSON entry object and returns the correct token string for the current OS: entry.mac_sc on Mac, entry.pc_sc on PC. Returns null when the field is the string NULL or NONE, meaning the shortcut does not exist on this platform.
ShortcutMatchesEvent( shortcutString, keyboardEvent ) Match checker Takes a token string and a browser keyboard event. Returns true if the event satisfies the shortcut. Calls ParseShortcutString internally, then checks modifier flags and physical key code against the parsed result.
ShortcutToKeyCodes( shortcutString ) Keyboard lighting Takes a token string and returns the array of browser key code strings that need to be lit on the graphical keyboard display. Used only by the lighting system, not by match checking.
RenderShortcutChips( shortcutString, isLongForm ) Chip renderer Takes a token string and a boolean. When isLongForm is true (shortcuts with one or two tokens), renders wide chips with word labels. When false (three or more tokens), renders compact chips with symbols only. Canonicalises token order before rendering. Returns a DOM element.
